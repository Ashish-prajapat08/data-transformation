# V0 implementation and verification

## Initial assessment

The supplied repository had Pandas CSV/Excel/database/API ingestion, mean/mode cleaning, a one-node LangGraph LLM text wrapper, FastAPI cleaning routes, and a Streamlit page. Endpoint spelling/ports and API request construction disagreed. Credentials were embedded in demo scripts; imports initialized the LLM and required a key. There were generated bytecode files, a UTF-16 environment-wide dependency freeze, no real automated tests, and no Git metadata.

Reuse/refactor: preserve file-ingestion concepts, Pandas tools, FastAPI/Streamlit surfaces and old launch/import locations. Replace free-form model dataframe rewriting, implicit imputation and the one-node graph. Retire public arbitrary SQL/external URL ingestion from V0, and remove hard-coded credentials and generated bytecode. Dependencies are now scoped to the implemented product.

Sequence: security/inspection → deterministic tool contracts → structured graph/planning/approval → retries/entity/schema review → evaluation → Streamlit/API → persistence/audit → integrated verification. Evaluation fixtures were introduced alongside the first tools, rather than after implementation.

## Boundaries

- `models/migration.py`: strict Pydantic target, mapping, tool-call, plan, review, validation and trace contracts.
- `tools/`: Pandas operations; no model-generated code or arbitrary dataframe text parsing.
- `agent/state.py`: explicit typed migration state; records excluded from metadata serialization.
- `agent/planning.py`: metadata-based structured semantic LLM planner, semantic entity explanations and labelled deterministic baseline. Every proposal is guarded against known sources/targets, incompatible tools, schema-less imputation and changed retry mappings.
- `agent/graph.py`: real LangGraph graph with conditional entry/routing, approval stop, tool selection, validation feedback, bounded corrective replanning, review stop and completion. Checkpoints after graph nodes/tools make progress inspectable.
- `backend/service.py`: application approval/review/export rules. Corrections are constrained to rows in the pending issue, then validated again. Review batches are atomic at persistence; conflicting revisions fail.
- `backend/persistence.py`: SQLAlchemy typed-state/working-record storage plus separate evaluations. SQLite locally; PostgreSQL URL support. Approval/review boundaries are durable application checkpoints; the graph resumes with the persisted explicit state rather than an in-memory-only interrupt.
- `backend/main.py`: file creation, plan approval/background execution, polling, review, preview, audit, export, deletion and evaluation endpoints. File parsing/LLM execution run outside the async event loop.
- `app/app.py`: API-backed Streamlit migration/review/evaluation dashboard with progress polling and retained CSV download.
- `evaluation/`: independent clean fixtures, controlled injection, deterministic evaluators, metrics and runner.
- `scripts/`: original launch/import paths retained as compatibility facades.

A single orchestrator uses the LLM for semantic mapping, instructions, tool selection, validation-aware replanning and organization-name reasoning. Python transforms actual data. Human decisions always control ambiguous entity merges. Offline mode is a development/evaluation baseline and is never described as live Generative AI reasoning.

## Verification performed

- Compiled tool/model, graph, API and UI modules as each layer was added.
- Initial deterministic tool tests passed before graph implementation.
- Verified the graph directly against the injected repairable fixture: plan approval stop, execution and successful validation.
- Added API/service integrations and reproducible evaluation checks; verified CSV export against independent clean expected data.
- Rendered and exercised the actual Streamlit application with Streamlit AppTest against the actual FastAPI TestClient. Plan approval reaches a validated ready result without UI exceptions.
- Exercised XLSX ingestion, mapping review, failed validation and retry limits, human corrections, invalid corrections, entity keep/merge, rejection, export gating, restart review, optimistic version conflicts, persisted checkpoints, unknown source/tool rejection, secret-safe failures, duplicate headers, ambiguous dates and spreadsheet formula escaping.
- Final automated suite: **23 tests passed**, including actual UI rendering and plan approval.
- Executed four baseline evaluation scenarios and saved a measured report under ignored `evaluation/results/baseline.json`.

Live OpenAI calls and live PostgreSQL connectivity were not exercised. The installed LangGraph version emits Pydantic deprecation warnings; installed protobuf emits Python 3.14 compatibility warnings. Tests target Python 3.11–3.13 and Pydantic 2. These dependency warnings do not fail the exercised workflow.

## Practical limits

This is a small local V0, with no authentication, direct CRM imports, worker queue, encrypted storage or schema migration system for future DB changes. Tool progress is durable for inspection, but replay after a crash mid-execution requires a new run from the source file. Reviews resume from stored working records. Organization name matching is a candidate-generation heuristic; it cannot establish legal/customer identity. A merge is a reviewed keep-first deletion, not automatic conflict reconciliation.

Evaluation ground truth covers a small synthetic regression suite. Case-level validation accuracy means agreement on valid/invalid output, not exhaustive issue-level classification. Export completion and safe blocking are reported separately. Undefined metrics remain null, and neither model quality nor production performance is inferred from baseline results.


## NVIDIA provider addition

`LLM_PROVIDER=nvidia` selects `agent/nvidia.py` inside the existing LLM planner. `NVIDIA_API_KEY` and `NVIDIA_MODEL` configure NVIDIA independently of OpenAI. The transport uses the OpenAI-compatible NVIDIA endpoint, nonstreaming JSON responses with thinking disabled, schema instructions and strict local Pydantic validation. Missing keys, invalid JSON, invalid contracts and truncated outputs block execution. It does not change deterministic tools or approval rules.

`python -m scripts.check_llm` verifies a small synthetic live planning request after local credentials are configured. `data/demo_contacts.csv` provides a simple UI demo. Latest automated verification: 31 tests passed, including mocked NVIDIA transport, real graph execution, provider selection, entity-output parsing and invalid-output rejection. Live NVIDIA access was not exercised during implementation.
